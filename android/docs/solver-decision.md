## 1. Background & Constraints

The app must complete finite element solving **without network and without a server**
(privacy + usability requirements), and the v1 acceptance targets are:

- Error vs. analytical solution ≤ 5%;
- 100k-DOF solve ≤ 60 s (mid-range physical device, 8 GB RAM);
- Installable package within acceptable size (hundreds-of-MB scale).

Meanwhile the project already had a Python prototype (`/workspace/pocket-fea`, scikit-fem based,
with the cantilever-shelf / nail-in-wall / simply-supported-laminate templates), which validated
the accuracy and the engineering path.

## 2. Candidate Routes

| | Route A: Chaquopy + scikit-fem | Route B: CalculiX (NDK) | Route C: FEniCSx |
|---|---|---|---|
| Form | Python interpreter embedded in the app, pure-Python solve stack | C/C++ solver cross-compiled to .so, called via JNI | dolfinx + PETSc/MPI full-stack port |
| Prototype reuse | **Directly reuses the Python prototype code** | Needs a rewritten input-card conversion layer | Needs a rewritten UFL/Python driver layer |
| Dependency chain | numpy/scipy/skfem all have Android wheels | calculix sources + NDK toolchain | PETSc, MPI, HDF5 and other native dependency chains |
| 3D/nonlinear | Weak (memory & performance limited) | **Strong** (CalculiX native capability) | Strong |
| Integration cost | Low (Gradle-plugin level) | High (self-maintained NDK build) | **Infeasible** (see §4) |

## 3. Decision: Route A (Chaquopy + scikit-fem)

### 3.1 Rationale

1. **Low integration cost, already validated**: Chaquopy 17.1.0 (released 2026-10, free and open
   source Apache-2.0, Maven Central `com.chaquo.python`) has first-class support for AGP 7.3–9.4
   (this project's AGP 8.5.2); numpy/scipy have official Android prebuilt wheels, scikit-fem is a
   pure-Python package, and the build config needs only three lines of `pip { install(...) }`.
2. **Code reuse**: the solve kernel shares the same stack and language with the Python prototype
   (the `pocketsim` package); algorithm fixes and new templates sync at zero cost between desktop
   and app; the prototype's already-proven material library, template registry, and safety-grading
   convention (sf ≥ 2.0 safe / 1.2 ≤ sf < 2.0 caution / < 1.2 dangerous) carry over directly.
3. **Second-order element accuracy meets target**: the prototype uses CST constant-strain triangle
   elements with mesh-convergence refinement, and compared against strength-of-materials analytical
   solutions (cantilever deflection δ=PL³/3EI etc.) the error is ≤ 5%;
   see the evidence report: `../python/benchmark_report.md` (generated by the Python-side task,
   with per-template FEA-vs-analytical error tables and mesh-convergence data).
4. **Performance is achievable**: 2D linear elastic at 100k DOF corresponds to a sparse symmetric
   system; scipy (SuperLU) solves it in seconds on arm64; timeout protection is backed by the
   Python side's automatic mesh downgrade (the results page shows a "已自动降级网格"
   (mesh auto-downgraded) notice).

### 3.2 Accepted Costs

- The Python runtime + scientific stack grows the APK by ~150–250 MB (two ABIs) — acceptable for a lifestyle utility app;
- Python solves block at the C layer and cannot be cancelled mid-run — the downgrade mechanism substitutes for cancellation;
- scipy wheel versions are limited by Chaquopy repo coverage — fallback plan: item 2 of the README's "Known limitations" section.

## 4. Why Not FEniCSx (Route C Rejected)

FEniCSx (dolfinx)'s solve layer depends on the **full PETSc + MPI (and BLAS/LAPACK/HDF5) toolchain**:

- These libraries target HPC clusters, have no official Android support, and would require cross-compiling the entire dependency chain yourself (including adapting the MPI runtime to a single-process app sandbox) — engineering effort and maintenance risk far exceed the benefit;
- Chaquopy's pip repo does not provide Android wheels for these packages;
- Its core advantages (large-scale parallelism, automatic differentiation of weak forms) bring no gain for v1's 2D linear elastic scenarios.

**Conclusion: the dependency chain cannot be packaged inside the app — rejected.**

## 5. Route B (CalculiX / NDK): Evolution Direction for the 3D & Nonlinear Phase

Not done in v1, but kept as the established evolution route. Trigger conditions and pre-research points:

- **Trigger**: when v2 requirements enter 3D solid modeling, geometric nonlinearity, contact, or plasticity;
- **Pre-research**: cross-compile CalculiX `ccx` to an arm64 .so with the NDK, wrap a job-submission interface via JNI; pre/post-processing (mesh, contours) stays on the Python/Kotlin side, reusing v1's data pipeline (the FeaResult JSON contract is unchanged; only the `pocketsim.engine` backend implementation is swapped);
- **Transition strategy**: Routes A and B can coexist (template-level switch); 2D templates keep using scikit-fem.
